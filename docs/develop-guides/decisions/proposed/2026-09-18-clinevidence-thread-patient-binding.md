# 会话与患者绑定关系

状态：proposed
类型：architecture
Owner：backend/package/yuxi/services/conversation_service.py

## 问题

本记录面向 ClinEvidence 开发者与面试评审，承接[阶段计划](../../clinevidence-roadmap.md) M2 患者业务模型，回答一个会话内出现多名患者材料时的回答归属问题：医生在同一对话中上传两名患者的病历后提问，系统如何保证检索、回答与引用对应正确患者。

现有会话（Conversation）没有患者概念，聊天附件确认后进入 Project Workdir，未自动进入患者向量索引；通用知识库使用独立入库流程。仅依赖提示词区分患者是概率性约束：模型分不清跨患者代词指代，长对话后生成环节可能把 A 患者细节写入 B 患者回答。按[工程信任系统](../../engineering-trust.md)，前端守卫、prompt 与 schema omission 不是授权边界。

本批演示资料已脱敏且保留时间线，缺少稳定身份标识时自动身份核验不能证明文件归属。评测还需要可重复的批量装机路径，以及题库 session 到患者和分册范围的审核映射。本记录收敛 M2、M5、M6、M7 与 M11 的相关提案；换患者通过新会话完成。

非目标：不改变 EMR 对接与正式病历回写范围；不实现多患者对比功能；不约束结构化数据（检验数值、医嘱、诊断编码）的查询通道。

## 提案

### 会话模型

1. 诊疗会话创建时必须持久绑定 `patient_id`，绑定不可修改；普通知识会话可为空，不能访问患者通道。
2. 病历导入必须绑定 patient；visit 仅在有原文依据时指定，未知时保持 `unassigned`。来源片段与不可变快照继承患者归属。
3. 同一会话不允许切换患者。具有可靠身份冲突信号的文件被隔离，缺少身份信号的文件等待归属确认；脱敏文件误归属不能保证被自动发现。查看另一患者必须新建会话。
4. 多患者对比是二期显式功能（独立会话模式、明确选择对比对象、引用强制标注患者身份），通过独立提案引入，不是默认行为的隐式推论。

### 检索与生成的作用域

5. 患者通道检索的患者/就诊/快照作用域由服务端从会话绑定的"当前患者"解析；模型传入的患者标识不参与作用域计算，工具层忽略或拒绝不一致的患者参数。
6. 每轮回答的患者证据引用携带患者标识与快照版本；引用验证要求引用可回溯到当前患者已发布快照的来源片段。
7. 摘要、记忆与缓存按患者和快照隔离，另一患者会话的内容不得进入当前模型输入。
8. 知识通道（指南、文献、院内规范）无患者属性，不受会话患者绑定影响；两通道融合时，患者证据与知识证据分别标注来源通道。

### 事实 Owner 分工

9. 会话绑定关系与上传归属约束由患者业务模型（M2）拥有；患者通道工具的作用域解析与引用验证由工具契约（M6）拥有；摘要与缓存的跨患者隔离由上下文压缩链路（M7）拥有。提示词只描述行为，不承担隔离责任。

### 脱敏归属、种子导入与分册范围

缺少稳定标识时 `identity_fingerprint` 为空，身份检测结果保留 `identity_unverified`。归属确认单独记录状态、确认人、时间、依据与文件/清单 hash；患者 Owner 可确认本人患者资料，种子操作员需显式种子导入权限及目标患者写入权限。已审核清单可批量确认归属，不能把结果改成自动匹配、覆盖身份冲突或代替内容审核。隔离以登记归属为前提，错误归属需要人工纠正。

管理 CLI 与 thread 上传复用拟建的 `patient_record_ingest_service`。CLI 允许无 conversation 的每患者批次，复用持久任务、解析审核、索引验证与 PG 快照发布，不能直接写表或向量。源文件 hash、稳定 patient/document key、审核清单及幂等键支持重试；运行结果回读实际版本与快照 ID。M11 在干净环境重灌并比较源 hash 与快照成员关系，部分失败不声明整套评测就绪。

分册是文档组织单元；encounter 由原文就诊关系和时间线确定，未知不猜测，跨就诊分册可按有依据的页段关联。题库 session 经审核映射为 patient key 和精确文档/页段范围，装机后解析到已发布快照中的版本及解析修订。原题复现由服务端在检索、原文读取和引用上执行“快照成员 ∩ 题目范围”，歧义范围阻断；患者全量综合使用完整患者快照并单独审核 reference、单独报告评分。预期答案和预期证据不注入被测 Agent。

## 替代方案

| 方案 | 收益与代价 | 选择 |
|---|---|---|
| 不可变单患者会话与服务端作用域共同执行 | 归属清晰、可验证；查看其他患者需新建会话 | 采用 |
| 自由多患者会话，依赖提示词区分 | 不需要新增绑定关系；约束概率性、不可验收，跨患者泄漏不可防 | 不采用 |
| 仅前端强制患者选择 | 实现小；API 直调与工具调用绕过呈现层，属伪安全 | 不采用为安全边界 |
| 同会话确认后切换患者 | 少建会话，但摘要、历史引用和缓存切换复杂 | 首期不采用 |
| 脱敏文件逐份点击确认 | 操作直接，但批量评测装机成本高 | 保留交互入口，同时提供按审核清单批量确认 |
| 种子脚本直接写数据库和 Milvus | 装机快，但绕过生产发布流程，形成两套事实源 | 不采用 |
| 分册编号直接作为 encounter | 映射简单，但可错误拆分同次住院或合并多次就诊 | 不采用，依据不足保持未归属 |

## 风险

- 会话绑定与上传归属扩展现有会话、文件和任务流程；验收覆盖新建另一患者会话和清单批量确认。
- 服务端作用域解析与现有工具参数 schema 存在调整成本，M6 契约需先于工具实现定稿。
- 摘要与缓存的患者隔离跨越既有 checkpoint 机制，M7 必须验证不同患者会话的模型输入。
- 默认单患者行为可能被评审认为限制效率；代价已在本记录接受，多患者对比走二期提案，不修改默认行为。
- 脱敏资料的错误人工归属无法由身份检测兜底；清单需要审核并保留版本，批量确认不表示临床金标准认证。
- 分册就诊归属未决时可完成文档范围评测，但不能宣称 encounter 粒度已审核；患者全量评测需要重新审核原分册 reference。
