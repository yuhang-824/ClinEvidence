# ClinEvidence 秋招二次开发阶段计划

本页面向项目开发者和面试评审，给出从 Yuxi 基座到可复现医疗 Agent Demo 的执行顺序、交付物和验收门槛。项目已完成命名与[第一批依赖精简](decisions/implemented/2026-09-17-clinevidence-local-pdf-scope.md)，本地合成 PDF 入库链路已验证；下面的医疗 M0—M11 仍须逐项验收。15 个全职工作日是预算，依赖模型、数据权限、OCR 环境和临床复核资源及时可用。

## 目标与范围

ClinEvidence（循证医助）计划支持主管医生基于患者纵向病历与医学知识进行带证据的问答，以及主任医生按规则检查完整病历并获取质控报告与评分表。采用单 Agent 与受控工具，复用 Vue、FastAPI、LangGraph、PostgreSQL、Redis/ARQ、Milvus、MinIO 及现有权限和任务机制。知识图谱、联网搜索与外部知识库连接器已移除，知识库以本地 PDF 文档导入为主。

首期支持浏览器操作和手动上传，以合成资料或获准使用的数据演示。EMR 对接、医嘱执行、自动回写、签署归档、生产院内部署和多 Agent 协作不在本轮验收范围。医生自行判断与修改正式病历。软件测试和规则计分结果分别记录，不能据此宣称临床有效性。

## 文档依据与取舍

依据用户提供的《Yuxi医疗Agent二次开发执行计划与实践清单》《院内诊疗辅助与病历质控项目计划书 V2.0》《医疗Agent秋招Demo执行与阶段计划书》整理。原文中的命令、旧项目名、部署建议和简历模板作为需求参考，不自动执行或认定为已完成事实。

执行顺序采用 Yuxi 专项清单的 M0—M11 与 15 天预算；保留 V2.0 的患者、时序、证据与全病历质控约束；采用秋招计划的本地可复现 Demo 优先和实测证据要求。文档曾提出 pgvector 与 Milvus 的不同选择，本项目已有 Milvus 装配，先复用并测量，不在命名阶段替换存储。代码已集成 Langfuse，先复用应用自身的 Run 与模型/工具审计；不把 LangSmith 或任何外部观测服务新增为运行前置条件。

资料数量仍待审计：文档提到三份样本、100 份病历、800 道题，当前任务仅提供三份计划书。不能据此认定患者数、题目金标或医院规则已可用；计划书引用的病历内容不进入公开测试集。

## 阶段与验收

每阶段依赖前一阶段的核心验收。日志从 M0 贯穿，评测从 M1 设计、M4 持续运行；各模块配最小界面，M10 再统一操作流程。每阶段独立变更、验证与审查，失败时先缩小病例或规则范围。

| 阶段 / 预算 | 可执行任务 | 交付物 | 完成标准 |
|---|---|---|---|
| M0 基座验证 / 第 1 天 | 安装并检查 Compose；锁定源码、依赖和模型配置；用合成文档走上传→解析→入库→检索→问答 | 基线环境记录、真实调用链、复用与新增边界 | readiness 就绪；回读文件、检索结果和同 Run 最终回答；重启后可重复。源码版本缺失则明确记录，不能猜上游 commit |
| M1 数据审计 / 第 2 天 | 生成文件哈希清单；核对患者与就诊归属；将题目分为患者事实、时间线、通用知识、患者结合知识、质控、信息不足；按患者分组冻结 | 数据清单、题目审计、split manifest、首批 20 个带原文金标的问题 | 同患者及文件版本不跨组；无证据题不参与证据召回率；抽查 10 份病历及 50 题，数据不足时报告实际 N；确认数据可用于何种模型与公开演示 |
| M2 患者业务 / 第 3 天 | 在 PG 增加患者、就诊、导入批次、来源片段和不可变快照；复用现有文件、会话和任务；设计向量写入后校验并发布快照 | ER 图、迁移、repository/service、六类查询与执行计划 | 真实 PG/HTTP 验证重复导入、越权、回滚；失败批次不进入已发布快照；历史引用能回读。六类 SQL 覆盖患者文件、快照片段、回答证据、重复导入、未完成任务、评分明细 |

| M6 单 Agent / 第 8 天 | 沿既有 BaseAgent 接入四个只读工具：read_patient_context、search_patient_records、search_medical_knowledge、read_evidence_excerpt；结构化回答与引用验证 | 工具契约、提示词版本、实际工具轨迹、带引用对话 | 后端验证访问范围；跨患者/快照/伪造引用负向测试失败；不足时说明缺项；检查实际工具集合，医疗 Agent 不暴露委派能力 |

## 代码落点与复用边界

[架构地图](https://github.com/yuhang-824/ClinEvidence/blob/main/ARCHITECTURE.md)拥有基座的实际边界。医疗页面放入 `web/src/views` 并通过 `web/src/apis` 访问接口；HTTP 适配在 `backend/server/routers`；用例在 `backend/package/yuxi/services`；查询和可见性在 `repositories`；模型与迁移遵循 `storage/postgres` 的唯一迁移 Owner。M2 实施前先确认实际 schema 迁移入口，不另起自动建表路径。

解析与检索扩展现有 `knowledge`；医疗 Agent 与工具沿 `agents` 注册。普通请求继续经过 Message/AgentRunRequest、FIFO、事务提交、ARQ 和 worker，结果绑定同一 Run。长导入和质控优先复用 Durable Task；禁止用临时内存任务代替终态持久化。M6 中单 Agent 限制仅适用于新增医疗 Agent，基座通用能力继续保留。

## 评测口径与阶段门槛

Recall@K 以每题被召回的金标准原文证据数除以该题全部金标准证据数，再宏平均，并报告有效题数。Hit@K 单独报告命中文档、页或片段的粒度。事实正确率、引用定位正确率、证据支持率、合理拒答率、可回答题误拒率、质控 precision/recall 与覆盖率分别记录。延迟报告同环境 P50/P95、样本数、缓存条件、模型与 token；不预填性能或准确率目标为结果。

M4 门槛是可定位原文且有逐题基线；M6 门槛是工具、引用、权限与真实请求贯通；M9 门槛是规则可解释、分数可复算、未决项可见；M11 门槛是版本、数据、配置、命令与原始输出可复现。任一门槛失败时，优先修复主链路或减少规则数量，不继续堆叠展示功能。

## 个人实践与面试产物

亲自完成或逐行解释核心切片函数、六类 SQL、一个患者查询工具、一个确定性规则与评分函数；亲自检查实际模型上下文、至少 30 个检索失败案例和一次 worker 中断后的数据库状态。AI 辅助范围、上游能力与自己的新增实现分别说明。

五分钟演示依次展示早期快照问答及原文定位、后续资料改变依据、全病历质控与导出、一次受控异常及日志、固定评测与未解决案例。简历只填冻结评测实际得到的 x/n 和改善值；未完成项继续留在本计划。原始病历、题库、医院规则表、凭据及含正文日志保存在受控环境，不随代码上传。
